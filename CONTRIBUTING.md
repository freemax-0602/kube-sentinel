# Contributing Guide — KubeSentinel

## 1. Общие правила

- Вся разработка ведётся через отдельные Git-ветки.
- Прямые коммиты в `main` запрещены.
- Изменения в `main` попадают только через Pull Request.
- Каждый Pull Request должен быть связан с задачей Trello.
- Перед слиянием необходимо пройти CI и Code Review.
- Один Pull Request должен решать одну логическую задачу.

## 2. Именование веток

Формат:

`<type>/<task-id>-<short-description>`

Допустимые типы:

| Тип | Назначение |
|---|---|
| `feature` | Новая функциональность |
| `fix` | Исправление ошибки |
| `refactor` | Рефакторинг без изменения поведения |
| `test` | Добавление и изменение тестов |
| `docs` | Документация |
| `chore` | Настройки, зависимости, инфраструктура |
| `experiment` | Экспериментальные ML-исследования |

Примеры:

- `feature/DATA-000-dataset-preparation`
- `feature/DATA-003A-preprocessing`
- `feature/K8S-002-log-collector`
- `feature/ML-002-pytorch-mlp`
- `fix/API-002-invalid-payload`
- `docs/PRJ-002-architecture`

Правила:

- Использовать латинские символы.
- Не использовать пробелы и кириллицу.
- Краткое описание писать в `kebab-case`.
- Идентификатор задачи сохранять в формате Trello.

## 3. Оформление коммитов

Используем Conventional Commits с идентификатором задачи.

Формат:

`<type>(<scope>): <description>`

Допустимые типы:

| Тип | Назначение |
|---|---|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `docs` | Документация |
| `test` | Тесты |
| `refactor` | Рефакторинг |
| `perf` | Оптимизация производительности |
| `build` | Сборка и зависимости |
| `ci` | CI/CD |
| `chore` | Прочие технические изменения |

В качестве `scope` используем идентификатор задачи Trello.

Примеры:

- `feat(DATA-000): add Kubernetes audit log samples`
- `feat(DATA-003A): implement initial log parser`
- `feat(K8S-002): implement pod log collector`
- `feat(ML-002): add PyTorch MLP model`
- `fix(DATA-003B): handle missing timestamps`
- `test(API-002): add inference endpoint tests`
- `docs(PRJ-002): document component contracts`

Правила:

- Описание коммита писать на английском языке.
- Использовать повелительную форму: `add`, `fix`, `implement`, `update`.
- Один коммит должен представлять одно логическое изменение.
- Не использовать бессодержательные сообщения вроде `fix`, `update`, `changes`, `final`.
- Не включать в коммиты секреты, токены, локальные окружения и большие датасеты.

## 4. Pull Request

Заголовок:

`[TASK-ID] Short description`

Пример:

`[DATA-000] Prepare Kubernetes audit dataset`

Описание Pull Request должно содержать:

- Ссылку на задачу Trello.
- Краткое описание изменений.
- Способ проверки изменений.
- Результаты тестирования.
- Известные ограничения.

## 5. Code Review

- Автор Pull Request назначает второго участника Reviewer.
- Reviewer проверяет корректность реализации, читаемость, тесты и соответствие задаче.
- Автор исправляет замечания до слияния.
- Слияние разрешено после успешного CI и одобрения Reviewer.
- Автор не должен самостоятельно одобрять свой Pull Request.

## 6. CI и качество кода

Перед слиянием должны успешно выполняться:

- `ruff check .`
- `pytest`
- Docker build, если он настроен для соответствующего компонента.

Новые функции по возможности сопровождаются тестами.

## 7. Работа с данными и ML

- Исходные датасеты не изменяются вручную.
- Источник и лицензия каждого датасета документируются.
- Большие датасеты и модели не добавляются непосредственно в Git.
- Преобразования данных должны быть воспроизводимыми.
- Для ML-экспериментов фиксируются конфигурация, seed, метрики и версия датасета.
- Нельзя допускать утечку данных между обучающей и тестовой выборками.

## 8. Завершение задачи

Задача считается завершённой, если:

- Реализация соответствует требованиям Trello.
- Добавлены необходимые тесты и документация.
- CI успешно пройден.
- Pull Request одобрен.
- Изменения объединены с `main`.
- Карточка Trello переведена в `Done`.
